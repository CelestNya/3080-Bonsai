# 在 3080 笔记本上跑 27B 三元量化：一次从 7 tok/s 到长期服务的完整调优实录

> 硬件：RTX 3080 Laptop 10GB（951GB/s，功耗上限 340W）+ 16GB 内存
> 模型：Bonsai-2-27B，Qwen3.8-27B 的三元量化版，权重只有 -1/0/+1 三种值，1.75 bit
> 引擎：PrismML 的 llama.cpp fork（llama-kvmem-server，带 KV 分层换页）
> 最终状态：decode 51-93 tok/s（视模式与投机命中率），prefill 750-1050 tok/s，256K 上下文，开机双击即用

这篇帖子记录整个调优过程。结论都带数据，数据都是控制变量测的。

## 起点是一次彻底的误判

模型跑起来，decode 7.4 tok/s。GPU 时钟 210MHz。

我第一反应是架构问题：三元量化的自定义内核是不是不支持 sm_86？于是去查内核、换分支、重编译，折腾一圈毫无改善。最后才想起来看一眼最基本的东西：

```
nvidia-smi --query-gpu=clocks.sm,power.draw,power.limit --format=csv
```

**功耗墙锁在 100W**（上限 320W）。一张 3080 被按在 100W 上，什么内核都是白搭。解锁：

```
nvidia-smi -pl 320
```

decode 直接 7.4 → 110 tok/s，**15 倍**。时钟回到 1935MHz，功耗 285-309W。

这个设置重启失效，必须写进启动脚本。

## 引擎选型：自己编译是负收益

Bonsai 的三元格式（PTQ1_0，GGUF type 143）是 PrismML 私有格式，主线 llama.cpp 不认，只能用他们的 fork。 fork 的预编译包里带 llama-kvmem-server——除了推理内核，还内置 KV 分层换页（显存放热数据，超出部分溢出到内存池）。

我对比了四种方案，同一模型同一参数只换引擎：

| 引擎 | decode (tok/s) | 备注 |
|---|---|---|
| KVMem 包预编译引擎 + --no-kvmem | 94.7-97.9 | 最终采用 |
| 同引擎 + KVMem 检索模式 | 83.5 | 短上下文时换页机制是纯开销 |
| 自编译 sudoingX bonsai2 分支 | 70.4 | |
| 自编译 combo 分支（理论 +15-25%） | **10.4** | 比预编译慢 9 倍 |

自编译那条路全是坑：某个 CMake 开关组合会让 ptxas 内核编译爆炸；构建还会卡在 npm/UI 打包步骤，要 -DLLAMA_BUILD_UI=OFF。理论收益 +15-25% 的分支，实测只有预编译的十分之一。**社区"优化分支"的 README 数字和你的工具链产出的二进制是两回事**。

## 编译期和参数期的隐藏坑（都是 2-20 倍的差距）

这几条每一个都是实打实测出来的：

**1. FA_ALL_QUANTS 必须开。** 混合 KV 缓存（K 用 q8_0、V 用 q4_0，省显存的常规操作）在 CMake 默认配置下，flash attention 会**静默回退 CPU**。prefill 从 1082 tok/s 掉到 49.6，差 21.9 倍，日志里一个字的提示都没有。排查方法：KV 全 f16 与混合 KV 做对照，一眼定位。

**2. 静态编译优于 DLL 拆分。** BUILD_SHARED_LIBS=ON 时 decode 从 67 掉到 36。

**3. prefill 走 cuBLAS。** GGML_CUDA_PTQ1_0_MMQ_MAX_BATCH=0，prefill +51%。

**4. GGML_CUDA_BATCH_INVARIANT=1 是投机解码的命门。** 它保证草稿和验证的 logits 逐位一致，但只覆盖 1-4 列的输出——所以 --spec-draft-n-max 最大 3，设 4 会静默失效。

**5. 一堆没用的**：加大 ubatch 无收益甚至降速；ngram 投机在混合注意力（3:1 GDN:full）模型上静默失效；--mlock 在 Windows 上无效。

## profiler 说：瓶颈在计算，不在带宽

并发 nvidia-smi 采样，按请求阶段切分样本：

| 阶段 | SM 时钟 | GPU 利用率 | 显存带宽 | 功耗 |
|---|---|---|---|---|
| prefill | 1898MHz | 97% | **18%** | 302W |
| decode | 1830-1885MHz | 87-90% | 47-49% | 289-303W |

prefill 时带宽只用了 18%。这个数字直接毙掉了整个"堆带宽"优化方向（mmap 调优、KV 再压缩、换 PCIe 5.0 的盘……）。根因是三元权重运行时解包（LUT 查表）加 Hadamard 逆变换，纯计算密集。旁证：3080 比 2080 Ti 快 3 倍，带宽只高 1.5 倍——快出来的是算力。

所以唯一有效的加速手段是 MTP 投机解码（+48%），外加把权重塞进显存。顺带辟个谣：网上流传的"MTP 接受率 0.82、226 tok/s"是 5090 跑非三元模型的数据被错误引用了。三元 MTP 的真实天花板 1.25-1.7 倍，且接受率强依赖任务类型：代码 0.77-0.94，散文只有 0.48-0.58，跨任务比速度没有意义。

## KVMem：长上下文的钥匙，也是内存刺客

KVMem 的价值只有一个：上下文超过显存时的分层换页。短上下文它纯粹是负收益（83.5 vs 94.7）。

调出来的甜点：
- GPU 驻留 budget 40960 token：40K 以内 decode 39-73 tok/s
- 越过 budget 进换页区，decode 掉到 6-10 tok/s，但 250K 的"大海捞针"召回依然全对——慢，不错
- prefill 换页后还有 500-700 tok/s

**两个必须知道的坑**：

1. **CPU 池是启动即整块提交的**。--kvmem-cpu-gb 8 意味着进程 commit 直接涨 8GB，16GB 内存的机器空闲只剩 1.5GB。它是真金白银的内存开销，不是"用了才算"。
2. **NVMe 层在这个构建里被编译禁用**（KVMEM_ENABLE_NVME=OFF），传参直接 exit 1。

还有一个反直觉的实测结论：**衰减的触发条件是"缓存中所有序列的总量"越过驻留上限，不是单个请求的长度**。56K 的单文档全速跑（decode 33.8），但两个 13K 的会话交替切换，每次切回都是 cache=0 全量重算（KVMem retrieval 模式不保留非活跃会话的工作集，代价约 1.15 秒/千 token）。多会话场景要按"所有会话之和"来算预算。

## 服务化：从跑通到能过日子

跑通和能过日子之间隔着一堆工程细节，每一条都是踩出来的：

**启动脚本必须自带的东西**：
- `nvidia-smi -pl 320`（功耗墙，重启失效）
- `echo [%DATE% %TIME%] EXITED code=%ERRORLEVEL% >> service.log`——**静默退出不抓退出码就永远不知道为什么死**
- 端口守卫：启动前检查端口是否已被占，被占就退出。没有这个，双开实例会让后来者无限重启循环，每 5 秒刷一条日志

**不要看门狗**。我最初写了"崩溃自动重启"循环，后来发现它分不清"崩溃"和"启动失败"——端口被占时第二个实例会永远重试下去。而且自动重启会掩盖问题：服务死了拉起来，服务又死了又拉起来，你永远不知道它为什么死。改成单发模式：退出就退出，退出码留档，人来了再看。

**计划任务的坑**：任务跑在登录会话里会弹控制台窗口（我的选择：可见，好管理）；笔记本记得插电——「电池模式暂停任务」会在拔电时静默停掉你的服务。

**多会话的真相**：--parallel 只支持 1（引擎限制），并发请求整单串行排队。webui 开两个会话，第二个"卡住"其实是在排队。手动停止（断开连接）服务端 2-3 秒内取消，这个是好的；但停止后立刻重跑同一轮，KVMem 缓存会被判失效（日志 cache=0），20K 上下文全量重算 25 秒不流字——观感像卡死，其实是换页重算。

## 一次"抓幽灵"的排查

服务有时候会"死掉"：webui 生成到一半流断了。我花了很大力气排查：抓退出码、写确定性复现脚本、做对照实验、给引擎作者所谓的补丁方向找证据……最后发现**服务从来没有自发崩溃过**——那些"进程退出"事件全部对应人为操作（手动重启、我自己的测试进程误杀）。我在解决一个不存在的问题。

排查过程本身留下了一整套可复用工具：退出码日志、确定性复现脚本、逐层变量隔离。后来真正的问题（下载文件被塞了 16 字节垃圾头导致 GGUF 魔数损坏）就是靠这套流程 20 分钟定位的——文件头 hex dump 一眼看到 "Entry not found"，解析 KV 元数据数出张量总数，重建 40 字节文件头，修复完成。

镜像站的文件也不能直接信：某个镜像站会在文件头塞 16 字节错误信息再跟上完整数据——文件大小对、扩展名对、SHA256 全错。入库前校验哈希。
